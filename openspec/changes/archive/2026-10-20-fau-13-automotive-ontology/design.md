## Context
FAU-13 implements ADR-001/005/009/012 without resolving DEC-001. Existing knowledge.read and knowledge.publish policies are sufficient; no Entra catalog expansion.
## Decisions
One bounded ontology catalog per tenant is an aggregate. POST creates a draft; PUT replaces its concepts, relationships and rules atomically with If-Match. This allows coordinated concept deletion/reference edits without intermediate invalid graphs. Stable string IDs are explicit synthetic domain identifiers; concept kind/system, relationship kind/endpoints and rule system remain stable across revisions; rule conditions/outcomes may evolve under the same ID with version provenance. DELETE is represented by omission from a replacement draft; approved history remains immutable.
Concept kinds: subsystem, component, symptom, classification, severity, applicability, remedy. Relationship catalog: is-a (same kind), part-of (component/subsystem to subsystem), indicates (symptom to classification), classifies (component to classification), mitigates (remedy to classification), applies-to (applicability to component/subsystem). All edges same system; is-a and part-of are acyclic. Bounds limit CPU and request size.
Rules are conjunctions of symptom concept IDs with optional exact synthetic model/software applicability. Results identify classification/severity and allowed remedy kinds. Priority descending, then specificity (symptom count plus exact applicability) descending determine precedence; stable ID orders equivalent matches. Potentially overlapping equal-rank rules with different outputs reject400. Evaluation validates known same-system symptoms and explicitly returns no-match; this is no diagnosis or guidance. A winning rule returns all matched IDs, immutable input, publication, actor/time, and explanation. Retained evaluation results never recompute on GET.
Publications use increasing aggregate versions and preserve approver/time and full content. Evaluation requires an explicit approved version, preventing accidental latest-version drift. ClassificationVersion means exact ontology publication version. Old approved classifications stay resolvable after draft deletion/new publication; unavailable store maps to KnowledgeException503.
All management and draft/history reads require knowledge.publish. Approved reads/evaluation require knowledge.read. Evaluation creates server IDs and stores results atomically with actor/client audit and idempotency replay, with tenant isolation. Create/publication/evaluation retries precede dependency/version revalidation. PUT requires strong ETag; retryable operations require 1-100 ASCII key. Canonical payload normalizes unordered ID collections.
## Storage and risks
IOntologyStore requires detached snapshots, cross-process atomic versions, publication/replay/audit/evaluation rollback and restart retention. Production UnavailableOntologyStore always503; tests alone use locked copy-on-write memory. Future relational adapter must prove durability and coordinate callers; no current durable persistence claim. Immutable published versions are never withdrawn/reassigned by this API, allowing exact FAU-11 validation across transactions.
## Verification
Unit tests cover all kinds/systems, invalid references/types/cycles, ambiguity/precedence, pinning. API tests exercise exact permissions, draft isolation, publication, classification integration, no-match, history, tenant/replay/concurrency/rollback and unavailable production. Full existing suite, format, locked restore, OpenAPI schemas/examples/baseline and exact-source Linux CI required. Browser UI/agent workflows belong to later tickets.
