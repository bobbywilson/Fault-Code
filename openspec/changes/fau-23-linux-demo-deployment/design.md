## Isolation and capacity
Dedicated /opt/faultcode-demo and project faultcode-demo. Dedicated API, Angular, Qdrant and hostname-specific HTTPS proxy; dedicated edge/private networks and Qdrant/TLS volumes. No shared Docker socket mount, host network, privileged container, external LALAI network/volume or shared database. Bound total limits leave capacity for lalai-runner and OS; preflight must measure and enforce available memory/disk/CPU and port availability again. Logs rotate. Images pinned by verified digest and source revision. No global prune, Docker restart, LALAI reload or runner environment change.

## Delivery
Feature branches start from development; PR validation and review precede development/main merges. Only a successful same-source main CI set can build/publish immutable GHCR images and invoke the fixed Fault Code deployment receiver. GitHub environment demo-production, least privileges, pinned host key, no arbitrary root shell, no deployment from pull-request workflow_run payloads, concurrency cancellation disabled. Check current main SHA to prevent stale deployments. Receiver permits only fixed repository image digests and a validated source SHA; release/config paths are owned by root, and secrets are server-managed mode0600. Deployment account must have no general Docker membership or unrestricted sudo. Bootstrap/access expansion requires concrete action-time approval before server mutation.

## HTTPS and domain
Use only existing faultcodeai.com apex and www. Export current zone and authoritative answers before edits; retain NS/MX/TXT/SPF/DKIM/DMARC/CAA and unrelated records. Exact proposed A/CNAME changes require observed zone, never replace whole zone. Host has no shared proxy: proposed dedicated Fault Code proxy may bind80/443 only after firewall/network and service inventory verifies no conflicts. TLS issuance uses free ACME with scoped storage/renewal; never remove unrelated certificates. Select implementation from existing approved Nginx stack and verify package/image provenance before installation. No shared restart.

## Rollback and teardown
Store previous accepted digest/version and server configuration reference. On failed health/version probe restore only Fault Code image selection and rerun acceptance. Retain data volumes; schema rollback needs migration/backup plan before a database is added. Teardown dry-run enumerates exact project labels, directories, routes, certificates and DNS records. Default stop/remove only Fault Code containers and networks, retaining volumes and backups. Deleting persistent data requires explicit approval; no global cleanup or LALAI resource removal.
